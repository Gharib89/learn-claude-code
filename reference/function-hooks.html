Function hooks

Claude Code mods, compressed. Everything marked verified was read out of the binary or the bundled plugin-authoring skill on this machine at version 2.1.272. Everything marked unverified is secondhand and needs checking against /plugin-types before you rely on it.

Turn it on

# Default-off in 2.1.272. Session-scoped.
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude

# Load a plugin from disk for this session; folder is watched, saves hot-reload.
claude --plugin-dir ./my-mod          # repeatable
claude --plugin-url https://...zip    # fetch a .zip for this session

claude --debug                        # every skipped hook and refused result
claude plugin validate ./my-mod       # what the engine thinks you hooked
/plugin-types                         # writes .claude/types/*.d.ts THE REFERENCE

Layout

my-mod/
├── .claude-plugin/
│   └── plugin.json     name, version, description
│                       "types": "./types/index.d.ts"  if you extend $
│                       "userConfig": {...}            becomes `options`
└── hooks/
    ├── hooks.json      { "modules": ["./mod.js"] }   ONE path, relative
    └── mod.js          TypeScript or JavaScript, exports register

verified hooks/ is a sibling of .claude-plugin/, never a child of it. Both failure modes here are silent: nesting hooks/ inside .claude-plugin/ still passes claude plugin validate, which reports success on the manifest alone, and a --plugin-dir path that does not exist is a [WARN] Plugin path does not exist line in the debug log with nothing on screen. Read validate's output for a second block naming your module:

Validating hooks: .../my-mod/hooks/hooks.json

  ❯ ./mod.js hooks: tool.call{tool=Bash}
  ❯ ./mod.js calls: $.store.set

The shape

export function register(on, options) {
  on(event, matcher?, hook)
}

async ($, e, next) => {
  // $     engine interface, the only way out of the module
  // e     event input, a plain value
  // next  the rest of the chain, then the engine itself

  return await next(e)            // pass through
  return await next({ ...e, x })  // rewrite what everyone below sees
  return { ... }                  // answer alone; engine never runs
}

No DOM, no Node. No fs, no require, no process global. JSX is available with h as the factory. A failing hook is skipped and the chain continues without it, unless its registration's .catch answers in its place.

turn.step is the odd one

It streams, so its hook is an async generator, the only form that loads there:

async function* ($, e, next) {
  yield* next(e)        // forward the stream, evaluates to the step result
  for await (const chunk of next(e)) { yield chunk }   // rewrite chunk by chunk
}

A chunk once yielded stays. A hook that fails mid-stream is left where it stood and the rest of the response comes from beneath it.

on("ui.render", { component: "AbovePrompt" }, async ($, e, next) => {
  const t = await $.ui.resolve(e)   // per-surface element constructors
  return <t.Box><t.Text>hello</t.Text></t.Box>
})

e.surface is terminal, desktop or mobile, and the element table differs per surface: mobile has no Input, Select or Client; terminal has no Svg but alone has Raster. A grid of coloured cells is one Raster, never a Box per cell.

Trees are validated against an element allowlist, a per-prop allowlist and size budgets. An invalid tree is silently not drawn; the engine draws its own and writes to the debug log:

ui.render (<Component>): a hook returned a tree that does not validate

When a drawing silently falls back, that line and the element's props type are the only two things worth reading.

Beyond one dispatch

A hook runs inside one dispatch with a budget. next.signal aborts when that dispatch is abandoned, and anything started for it should stop on it. Work that must outlive a dispatch starts in session.start, which fires once and is awaited before the first prompt.

Extending $

This is the composability story and the reason mods are more than hooks. A plugin can add a noun to $ in engine.create and ship its types as a contract: one self-contained .d.ts that exports the noun's types and declares it on the engine interface.

export type Topo = { ... }
declare module 'claude-code' {
  interface EngineInterface { topo: Topo }
}
// named in plugin.json as "types": "./types/index.d.ts"

A dependent plugin never copies that file. /plugin-types collects every enabled plugin's contract into claude-code-plugins/ beside an index, so the noun is typed on the dependent's $ automatically.

tool.call

verified Read out of claude-code.d.ts as /plugin-types generated it from 2.1.272. The event is the tool's own arguments spread flat beside two reserved fields, not nested under input:

e = {
  tool: "Bash",           // reserved: a rewrite is ignored by core
  tool_use_id: "toolu_",  // reserved: same id at every event of the call
  agentId?: string,       // absent on the main loop; pinned
  ...the tool's arguments // Bash: command, timeout?, description?, ...
}

A hook returns { deny: string } to refuse (the model reads the string as an error result) or { result, context? } to answer the call itself. Anything else is refused with returned the wrong shape (neither { result } nor { deny }) and the hook is skipped, so the call proceeds unguarded.

next(e) resolves to core's fuller object, { ref, result, text } plus isError: true when the tool reported an error. ref, text and isError are core's to set: a hook cannot fabricate an error result, it can only deny. Returning the object next gave you unchanged makes core reuse its own messages verbatim.
