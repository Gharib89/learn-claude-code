# Mission: Claude Code Mods

## Why

Ahmed spends his working day inside Claude Code and wants the interface to fit his hands, not the default shape. Mods are the first surface that lets the tool be reshaped from the inside, so the goal is twofold: tune his own daily CLI, then package what works and hand it to his team at IT Worx so they run one tuned setup instead of ten personal ones. Before either, he needs to know what a mod is actually allowed to do, because installing team-wide code that rewrites the agent's own interface is a security decision, not a preference.

## Success looks like

- Writes a mod from scratch that changes something he looks at every day, and has it loaded and visibly working in his own Claude Code.
- Can state precisely where mods sit relative to skills, hooks, plugins, output styles, and MCP servers, and picks the right one without guessing.
- Explains the mod permission and trust model well enough to justify, to a colleague, whether a given third-party mod is safe to install.
- Packages at least one mod for distribution and installs it on a second machine or account as a real consumer would.

## Constraints

- Already a heavy Claude Code user who has authored skills, hooks, and plugins: skip extension fundamentals, start at the mod API itself.
- Pacing is one lesson at a time, then react. No batched roadmaps.
- Lessons must be concise and finishable in a sitting.

## Out of scope

- Teaching skills, hooks, or plugin authoring as topics in their own right. They appear only as contrast when a comparison sharpens what a mod is.
- Terminal/TUI theory in the abstract. Only the parts a mod actually touches.
