Wrapping, not reacting

You have written shell hooks. They watch. A function hook stands in the middle of the operation and owns both what goes in and what comes back. That one structural difference is the whole feature, and porting a guardrail you already run is the fastest way to feel it.

The shell hook you already write

  prompt
    → engine decides
        → runs the tool
            → your script sees it
                → exit 2 to block

  You are downstream. You react
  to a decision already made,
  and the result has moved on
  by the time you read it.

The function hook

  prompt
    → your hook opens
        → next(e) → engine runs
        → your hook closes
            → returns the result

  You are the wrapper. You hold
  the input before it lands and
  the result before anyone else
  sees it, in one function.

If you have written Express middleware, you already have the shape. The payoff is not that it is tidier. It is that rewriting an input and annotating the result stop being two separate hooks that cannot see each other.

The contract

A mod is a plugin folder. Its hooks live in one module that hooks/hooks.json names, and that module exports register:

export function register(on, options) {
  on(event, matcher?, hook)
}

Every hook has the same three parameters, and the names are worth saying out loud because they are the mental model:

ParameterIsConsequence
$The engine interface: display, model, session, prompt, tools, filesystem, store, clock, network, process, settings, environmentThe module has no DOM and no Node. There is no fs, no require. Everything outside the module is reached through $, which is exactly what makes a mod restrictable.
eThe event's input, as a plain valuePass next({ ...e, field: newValue }) and the rest of the chain sees your version.
nextThe continuation: the other plugins, then the engine's own behaviourawait next(e) resolves to the result. Return without calling it and you have answered for yourself, which is how a mod denies something.

Port your git guardrail

You already block force pushes with a shell hook. Here is the same guardrail as a function hook, which is a deliberately small delta from what you know.

my-guardrail/.claude-plugin/plugin.json

{
  "name": "my-guardrail",
  "version": "0.1.0",
  "description": "Refuses force pushes, and says so in the result."
}

my-guardrail/hooks/hooks.json

{ "modules": ["./guardrail.js"] }

my-guardrail/hooks/guardrail.js

export function register(on) {
  on("tool.call", { tool: "Bash" }, async ($, e, next) => {
    const command = e.command ?? "";

    // Answer for ourselves: never call next, so the engine never runs it.
    if (/git\s+push\b.*(--force|-f)\b/.test(command)) {
      return {
        output: "Refused by my-guardrail: force push. Use --force-with-lease.",
        isError: true,
      };
    }

    // Wrap: hold the result, annotate it, hand it back up.
    const result = await next(e);
    if (/git\s+push\b/.test(command)) {
      $.store.set("last-push", new Date().toISOString());
    }
    return result;
  });
}

Note what the single function does that two shell hooks could not: it decides on the input and records something about the result, sharing the command variable across both moments.

The one thing in this file I could not verify

The field names on e for tool.call (e.command) and the shape of the object you return (output, isError) are my best reading, not a checked fact. The engine's own types are the authority and they move between releases. Confirming them is step 3 of the exercise below, and treating a plausible-looking field name as true is the main way people lose an afternoon here.

Run it

# The feature is default-off in 2.1.272. Turn it on for this session only.
CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir ./my-guardrail --debug

The folder is watched. Save the file and the module reloads, register runs again in a fresh environment, and timers from the old one are dropped. You do not restart Claude Code to iterate.

When a hook fails it is skipped and the chain continues without it. You get one dim line naming the plugin, the event and the reason. A mod that appears to do nothing has almost always been told why, in the debug log. Before you even start a session, claude plugin validate ./my-guardrail reports what the engine thinks your module hooks and calls.

Your exercise

  1. Build the three files above.
  2. Load it with the command above and try git push --force on a scratch repo. Confirm the refusal text appears and the push never happens.
  3. Run /plugin-types in that session. It writes claude-code.d.ts into .claude/types. Open it, find the tool.call event, and correct my guesses about e.command and the return shape.
  4. Add one thing the shell version could not do: use the result you got back from next(e) to change what the model is told.

Recall

A hook returns without ever calling next. What happens?

Not calling next short-circuits the chain. The other plugins below you and the engine's own behaviour never happen. This is the deny path, and it is why a function hook can refuse something before it occurs rather than after.

Where do an event's exact field names come from?

/plugin-types generates the declarations from the build you are running, which matters because the API is provisional. There is no published event reference, and the bundled skill describes the contract without listing field names. Regenerate after every update rather than editing the file.

Your mod needs to read a file on disk. What does it use?

The module runs in an environment with no DOM and no Node, so fs is not reachable by any spelling. Everything outside the module comes through $. That single chokepoint is also the answer to your security question: because every capability is a noun on one object, capabilities can be withheld from a mod you do not fully trust.
